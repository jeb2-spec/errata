# Anchors

The verifier in this repository proves the record has not changed since we
built it. It cannot prove we did not rebuild it and quietly re-seal. We
build the file, we hash it, we publish it, so a seal we make ourselves
proves internal consistency and nothing more.

An anchor closes that gap: the record's fingerprint, witnessed somewhere
outside our reach.

## How this record is anchored

Each published build of `data/errata.db` is stamped with
[OpenTimestamps](https://opentimestamps.org). The stamp submits the file's
fingerprint to several independent calendar servers, which aggregate it
into the Bitcoin blockchain. Once that happens, the claim "this exact file
existed by this date" is held by a ledger that nobody, including us, can
rewrite. Rewriting our history would require rewriting Bitcoin's.

The current build's proof ships beside the data as `data/errata.db.ots`.
Every rebuild changes the file, so a rebuild moves the previous stamp to
`data/anchors/<built>-<sha8>.ots`, named for the build it proves, and the
table below says where each build's proof is. A stamp is never deleted: the
prior state survives, which is the only thing that tells patching from
falsification.

## Check it yourself

```bash
pip install opentimestamps-client
ots info data/errata.db.ots                        # the current build's proof
ots -v info data/anchors/2026-08-31-2fa4a7cf.ots   # the first build's, in full
```

`ots info` reads the proof file and touches nothing else. It prints the
SHA-256 the stamp was made against, which you compare with the hash in the
table below, and the Bitcoin block heights the proof commits to. The `-v` form
prints every intermediate value, and the one on the line above each
`BitcoinBlockHeaderAttestation` is that block's merkle root, byte-reversed.
Reverse it, look the block up on any explorer, and see whether they match.
That path goes through us at no point.

`ots verify` is the single-command version and it needs a local Bitcoin node
to read block headers from. Without one it exits with a cookie-file error.
Note also that `ots verify` derives its target by removing `.ots` from the
filename, so it cannot check an archived proof whose build is not the file on
disk; use `ots info`, or `ots verify -d <the file hash from the table below>`
with a node.

Until 4 September 2026 this block offered `ots verify` on both lines, with no
mention of a node, and its archived example named a file that has never
existed. Neither command had been run. That is correction
`anchor-commands-nobody-ran`, and the first repair of it fixed the README and
left this block untouched while saying both were done, which two independent
reviewers caught before it was published.

**To regenerate an anchored file byte for byte, build at the commit it
names.** A stamp binds the file's hash, and the file carries a
`meta.source_commit` row recording the commit that produced it. That row is
deliberately outside the digest, so the internal seal survives a rebuild
anywhere while the file's own hash does not: rebuild at a different commit
and every row is identical but the bytes differ by that one value. Check out
the commit the file names, rebuild there, and the hash comes back. Verified
2026-09-04 by rebuilding this record on a merge commit: same digest,
different file.

While a stamp is still waiting for Bitcoin aggregation (usually less than a
day), `ots info` shows pending commitments from the calendar servers rather
than a block. After aggregation, `ots upgrade` completes the proof and the
stamp names the blocks itself.

**A note on how strong this is, and is not.** Once a stamp is confirmed, the
record's fingerprint sits in Bitcoin and we cannot reach it. That makes a
later rewrite **detectable**. It does not make one impossible: we could still
alter the file, and anyone who checked the stamp would simply find that it no
longer matches. The anchor buys detection by a stranger, not immutability,
and the difference matters enough to say plainly. If you see this project
described as having made its history unchangeable, that description is
generous beyond what we claim.
